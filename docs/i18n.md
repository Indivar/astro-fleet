# Translating a site

**This is optional.** A site with no `i18n/locales.json` never runs any of it: no files are written, nothing appears in the build log, and the language switcher stays hidden. If you only ever want one language, you can stop reading here and nothing in the template will ask you about it again.

If you do want a second language, this page walks through it from nothing to a live translated site. It assumes you can edit a JSON file and run a command in a terminal. It does not assume you know Astro.

---

## What you get

- English keeps the root of the site. `/about/` stays `/about/`, so every URL that ranks today is untouched.
- Each other language lives under its own prefix: `/es/about/`, `/fr/about/`.
- A language switcher appears in the header, listing only the languages that actually have the page you are on.
- A page is only published in a language once it is genuinely translated. A half-translated page is not written at all, rather than published with English showing through.
- Until you tell it otherwise, translated pages are visible to visitors but hidden from Google. [Why that matters](#why-new-languages-start-hidden-from-google).

The `starter` site ships with Spanish already set up, so you can look at a working example before doing your own.

---

## How it works, in one paragraph

Your site is written once, in English. You build it as normal. Two scripts then run: the first reads the finished HTML in `dist/` and pulls out every piece of translatable text; the second takes your translations and writes a complete copy of the site into `dist/es/`. Your English source files are never touched or duplicated. When you fix a typo in English, the old translation for that sentence retires itself and shows up as untranslated, so translations can never silently drift out of date.

---

## Step 1 — Tell the site which languages it has

Create `i18n/locales.json` in your site folder. Here is the starter's, which you can copy:

```json
{
  "site": "https://www.example.com",
  "locales": [
    { "code": "en", "label": "English", "english": "English" },
    { "code": "es", "label": "Español", "english": "Spanish", "reviewed": false }
  ]
}
```

| Field | What it is |
|---|---|
| `site` | Your site's address. **Must match `site:` in `astro.config.mjs`.** The canonical and alternate URLs are built from it. |
| `code` | The language code used in the URL and in `<html lang>`. `es` gives you `/es/`. |
| `label` | The language's name **written in its own language**: `Español`, not `Spanish`. Someone looking for Spanish scans for `Español`. |
| `english` | The English name, shown as a quiet second line in the switcher so you can find a script you can't read. |
| `reviewed` | `false` until a person who speaks the language has read the pages. See [below](#why-new-languages-start-hidden-from-google). |

English must be in the list, and it must be first.

## Step 2 — Turn on the two build steps

In your site's `package.json`, add the two i18n commands to the end of the `build` script:

```json
"build": "astro build && node ../../packages/shared-ui/scripts/search-index.mjs && node ../../packages/shared-ui/scripts/i18n-extract.mjs . && node ../../packages/shared-ui/scripts/i18n-build.mjs ."
```

Order matters: `astro build` first, then extract, then build. Adding a shortcut for re-running just the translation part is worth it:

```json
"i18n": "node ../../packages/shared-ui/scripts/i18n-extract.mjs . && node ../../packages/shared-ui/scripts/i18n-build.mjs ."
```

## Step 3 — Show the switcher

Pass `showLanguages` to `BaseLayout` on every page that should offer it:

```astro
<BaseLayout
  showLanguages
  title="About us"
  ...
>
```

It is off by default and safe to turn on early: the control ships hidden and only appears once a page really has a second language.

## Step 4 — Build once, to see what needs translating

```bash
bun run --filter your-site.com build
```

You will see something like:

```
i18n-extract: 122 units (875 words) from 5 page(s) -> i18n/strings.json
i18n-build: 5 page(s), 122 distinct unit(s), bar 90% of a page's units
  es: withheld, 0.0% of units, nothing translated
```

"Withheld" is correct at this stage. Nothing is translated yet, so nothing is published.

A **unit** is one block of text taken whole: a paragraph, a heading, a list item, a button label. Not one word and not one page. Counting whole blocks is what stops a translator being handed `of`, `or`, `to` as separate fragments.

## Step 5 — Get the text to translate

```bash
node packages/shared-ui/scripts/i18n-batch.mjs next sites/your-site.com es 100
```

That writes `i18n/.batches/es-next.json`, holding the next 100 untranslated units:

```json
[
  { "k": "70f8bb9a8a53", "en": "Home" },
  { "k": "b37456c4530b", "en": "Contact" }
]
```

It hands you the home page first, then whichever page needs the fewest units to finish. Finishing pages publishes pages; finishing scattered paragraphs only moves a percentage.

### Placeholders

Some strings contain numbered tags:

```
"Built <0>here</0> since <1>1960</1>."
```

Those stand for links, bold text, icons and line breaks in the original. Move them wherever the sentence needs them in the new language, but **keep every one of them, and do not invent new ones**. A translation that loses `</0>` would swallow the rest of the paragraph, so it is rejected rather than published.

`<0/>` with a slash is a standalone thing like an icon or a line break. Keep it, move it if the sentence needs it.

## Step 6 — Hand the text back

Write a file with the same keys and your translations:

```json
{
  "70f8bb9a8a53": "Inicio",
  "b37456c4530b": "Contacto"
}
```

Then merge it:

```bash
node packages/shared-ui/scripts/i18n-batch.mjs merge sites/your-site.com es my-translations.json
```

```
merged 122 into sites/your-site.com/i18n/es.json -> 122/122 (100.0%)
```

This is the only command that writes a dictionary, and it checks as it goes. It refuses a translation whose placeholders don't match the English, and it refuses broken characters. Catching that here means you find the problem in a command's output, not as an English sentence on a Spanish page three weeks later.

Repeat steps 5 and 6 until you reach 100%. You can stop and come back; nothing is lost between sittings.

## Step 7 — Build again

```bash
bun run --filter your-site.com build
```

```
  es: 5/5 page(s) shipped, 100.0% of units, noindex
```

`dist/es/` now holds a complete Spanish copy of the site.

## Step 8 — Have someone read it, then publish it to Google

Once a person who actually speaks the language has read the pages, set `"reviewed": true` in `locales.json` and rebuild. That single change removes the `noindex` and adds the language to your sitemaps.

---

## Why new languages start hidden from Google

A language with `"reviewed": false` is live for visitors: the switcher offers it and every link works. It carries `noindex, follow` and stays out of the sitemaps, so search engines don't index it.

This is deliberate. Google's spam policy names machine translation published without human review as **scaled content abuse**, and the penalty lands on the whole domain, not on the one language. Publishing twelve unreviewed languages to win traffic is a good way to lose the traffic you already have.

So the default is: visitors can read it, Google cannot, until a person says it is good. `reviewed: true` is that person's signature.

## Useful commands

```bash
# How much is done, per language
node packages/shared-ui/scripts/i18n-batch.mjs status sites/your-site.com

# Which pages are ready, and what each still needs
node packages/shared-ui/scripts/i18n-batch.mjs pages sites/your-site.com es

# Next slice of work
node packages/shared-ui/scripts/i18n-batch.mjs next sites/your-site.com es 100

# Hand a slice back
node packages/shared-ui/scripts/i18n-batch.mjs merge sites/your-site.com es file.json
```

## Things that surprise people

**"A page is missing in Spanish."** It is below the bar. A page is published in a language only when at least 90% of *that page's own* units are translated. Run `i18n-batch.mjs pages` to see what it still needs. This is per page rather than per site on purpose: a long blog archive would otherwise hold up the product pages indefinitely.

**"The language disappeared entirely."** A language only ships at all if its home page qualifies. A language with no front door has no entry point, so the switcher would be offering a dead end.

**"I fixed an English typo and the Spanish went back to English."** Working as intended. A unit's identity is a fingerprint of its English text, so changing the English retires the old translation instead of leaving a translation of a sentence that no longer exists. Re-translate that one unit.

**"The switcher is empty or missing."** It is hidden until a page has more than one language available. Check the build output for a `withheld` line.

**"I translated something that should have stayed in English."** Product codes, model numbers, email addresses, URLs and bare figures are skipped automatically. To protect anything else, add `data-i18n-skip` to the element and everything inside it is left alone.

**"My headings overlap in the translated pages."** Scripts like Devanagari, Gurmukhi, Thai and Arabic put marks above and below the letter and need more line height than a Latin display face set tight. Add a leading floor for those languages in your site's stylesheet:

```css
html[lang='hi'] :is(h1, h2, h3, h4, h5, h6) { line-height: 1.38 !important; }
```

## What each script does

| Script | Reads | Writes |
|---|---|---|
| `i18n-extract.mjs` | `dist/` (the finished English site) | `i18n/strings.json`, `i18n/pages.json` |
| `i18n-build.mjs` | `dist/`, `i18n/*.json` | `dist/<code>/`, sitemaps, switcher entries |
| `i18n-batch.mjs` | `i18n/*.json` | `i18n/<code>.json`, `i18n/.batches/` |

`strings.json` and `pages.json` are generated. Don't edit them; they are rewritten on every build. The one file you own is `i18n/<code>.json`, and `i18n-batch.mjs merge` is the only thing that should write it.

## Turning it off

Delete the site's `i18n/` directory and remove the two i18n commands from its `build` script. Nothing else depends on it.
